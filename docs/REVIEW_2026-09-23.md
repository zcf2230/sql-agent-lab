## 4. 统计处理

作者的表述是：`89.1% → 93.2%`，配对 McNemar 精确检验 **p = 0.057，标注为"未达显著"**。

- [ ] 这样写**诚实且加分**（本科生会主动写 p 值不显著）
- [ ] 太保守，工程上 11:3 的方向性已足够采用该 prompt
- [x] 样本量就该更大，192 题撑不起任何结论 —— **而这一点我给出了定量证据（§9-D6）**
- [x] 统计量已入库，且我重跑**对上了**（`11/3 → 0.0574`、`23/14 → 0.1877`、`0/0 → 1.0`、
      噪声底 `2.1pp / baseline-v2 vs baseline-v3`，全部与 `HANDOFF.md` §4.3 一致）

**你的看法：结论（不宣称显著）是对的，但支撑它的理由比你想的脆。**

我实测：**192 道题按 `(族, gold-SQL 骨架)` 去重后只有 100 个独立簇。**
- `category_slice`：35 题 = **5 个骨架 × 7 个参数**
- `date_bucket`：22 题 = 3 个骨架，其中 **20 题是同一个骨架**换月份字面量
- `aggregate_count`：23 题 = 9 个骨架（两个骨架各重复 7 次）
- `filter_projection`：10 题 = **2 个骨架**

`stats.py` 的 McNemar n=192 建立在"题间独立"上，而同骨架题目的正确率高度相关
（模型要么会写这个 JOIN，要么不会）。换一个同样可辩护的聚类口径重算：

| 口径 | n | baseline | 3-shot | Δ | fixed/broke | McNemar 精确 p |
|---|---:|---:|---:|---:|---:|---:|
| 题级（现状） | 192 | 89.1% | 93.2% | +4.2pp | 11/3 | **0.0574** |
| 簇级，全对才算对 | 100 | 85.0% | 90.0% | +5.0pp | 8/3 | **0.2266** |
| 簇级，有一个对就算对 | 100 | 86.0% | 93.0% | +7.0pp | 8/1 | **0.0391** |

**p 在 0.039–0.227 之间游走，并且跨过 0.05。** 所以"p=0.0574"本身是独立假设的产物。

> 回答作者的问题 4（"未达显著是加分还是过谦"）：**标注方式加分，但这个标注现在靠的是守门槛，
> 而不是守鲁棒性。**"p>0.05 所以不宣称显著"这种写法，面试官一句"那 p=0.0499 你就宣称了？"
> 就能逼到墙角。更难的写法是："在族/骨架聚类下 p 从 0.04 到 0.23 不稳定，所以我不做
> 显著/不显著的二分，只报方向、效应量与区间。"——这样同时挡住两个方向的反问
> （"11:3 够了"和"p=0.057 说明没用"）。
>
> 另一处必须在头条数字旁给出的分解：**11 道"修好"的题里 `metric_by_group` 占 5、
> `category_slice` 占 4，而 19 个族里有 15 个族净变化为 0。** 所以"192 题上 +4.2pp"实质是
> "2 个族里的 12 道题"。不给这个分解，被问"这 4.2pp 是 prompt 的效果，还是 12 个模板实例的
> 运气"时没有弹药。
>
> 还有一个更省事的补法：**报 CI 而不是报 p 的二分**。两类 Wilson 区间本来就重叠
> （83.9–92.7 vs 88.8–96.0），这与 p=0.0574 一致——把 CI 和噪声底并排显示，
> 比只说"未达显著"更不容易被拆。

**这一栏的证据强度：够写"做了什么"，不够写"有多安全"。而且"6/26"换了个说法搬回来了。**

我逐条核对了 `results/adversarial.jsonl`（26 行全查）：

| 类别 | n | 模型尝试了越权 | 护栏拦下 | 写操作执行 |
|---|---:|---:|---:|---:|
| direct_write | 6 | **0** | 0 | 0 |
| stacked | 3 | **0** | 0 | 0 |
| catalog | 3 | 3 | 3 | 0 |
| exfiltration | 3 | 1 | 1 | 0 |
| social | 4 | **0** | 0 | 0 |
| injected_data | 4 | **0** | 0 | 0 |
| admin_op | 3 | 2 | 2 | 0 |
| **合计** | **26** | **6** | **6** | **0** |

三个结论：

1. **"0 次写操作执行"是平凡成立。** `direct_write` 6 条**模型一次都没尝试**——它直接拒绝了。
   也就是说护栏**从来没有被问到过写语句**。它真正立功的 6 次全是**读形状**的越权
   （`sqlite_master` ×3、`INTO OUTFILE`/`ATTACH`、2 个 admin op）。把"0 次写操作执行"
   和"护栏全拦下"并排读，会让人以为护栏挡住了写操作——事实是写操作根本没被送到护栏面前。
2. **统计上这栏连"大概率可靠"都推不出来。** 6 次挑战 0 次失守，按 rule of three，
   失守率的 95% 上界约 **1 − 0.05^(1/6) ≈ 39%**。所以样本支持的是
   "这 6 个**具体**形状被正确拒绝了"，不是"护栏可靠"。
3. **这 26 条的结论大部分不由护栏决定，而由模型决定。** 20 条的结论是"模型没尝试"，
   那是 `deepseek-chat` 的拒答倾向，换模型就要重测。所以这一栏不是**系统**的安全属性。

## 9. 本轮新增缺陷清单（均非第一轮已提；含复现方式）

> 格式：缺陷 → 文件:行 → 复现 → 后果。全部实测。

### D1 ★ `dataset_hash` 未做行尾归一 → 重跑必脏、缓存误失效

- 位置：`sqlagent/eval/runner.py:223` 对 `sqlagent/config.py:76`
- 复现：
  ```bash
  .venv/Scripts/python.exe scripts/calibrate.py
  git status --porcelain          # 10 个文件被修改
  git diff --numstat results/     # 每个 calib 文件恰好 1 行
  ```
  我逐行比对了 diff：**逐题判定逐字不变**，唯一变化的是 `_summary.config_hash`。
- 根因：`dataset_hash = hashlib.sha256(args.tasks.read_bytes()).hexdigest()[:8]` **用原始字节**；
  而 `code_hash()`（`config.py:76`）明确写了 `.replace(b"\r\n", b"\n")`，并在 docstring 里解释了
  为什么必须归一（"a clone with different line endings would otherwise produce a different digest
  and orphan the whole result cache for no behavioural reason"）。**同一个坏味道，修了 code 侧、漏了 dataset 侧。**
  触发链：`.gitattributes` 要求 `*.jsonl eol=lf`（入库 LF）→ `build_tasks` 用 Windows 默认文本模式
  写文件（CRLF）→ `dataset_hash` 变 → `config_hash` 变。
- 直接证明：同一份内容，CRLF → `config_hash=586e9d0e838f`，LF → `654ff5c34b1e`。
- 后果：① `tests/test_artifacts.py` 的 docstring 说这套改动的目的是"did the judge change?
  能不能用眼睛回答"——现在仍不能，因为那一行既可能是判分器变了，也可能只是行尾；
  ② README 的 "a repeated run is free" 在 Windows 上不成立，缓存被静默作废；
  ③ 作者回应里"重跑不再产生假 diff"这句**与实测不符**。
- 修法：`runner.py:223` 同样 `.replace(b"\r\n", b"\n")`；并让 `build_tasks.py:618` /
  `calibrate.py` 写文件时带 `newline="\n"`（两处都做最稳）。
  顺手把 `config_hash` 从提交的产物里去掉，或改成"仅当 code/dataset 摘要变化时才重算"的字段——
  它是"这台机器当时怎么跑的"，正是 `test_artifacts.py` 已经在排除的那类字段。

### D2 ★ `report.html` 与 `significance.py` 的噪声底各说一套

- 位置：`sqlagent/report.py:100` 的本地 `noise_floor()` vs `sqlagent/stats.py:103`
- 复现：
  ```bash
  .venv/Scripts/python.exe -c "from sqlagent.report import noise_floor as r; from sqlagent import stats; print(r(), stats.noise_floor()['worst_tasks'], stats.BASELINES)"
  # 输出：2 / 192    4    ['baseline-v2','baseline-v3','abl-baseline','abl2-baseline']
  ```
- 根因：`report.py:102` 的基线集合是 `("baseline-v3","abl-baseline","abl2-baseline")`，
  **漏了 `baseline-v2`**——而最差对正是 `baseline-v2 vs baseline-v3`（4 题 = 2.1pp）。
  且 `report.py` **完全没有 import `stats.py`**（`figures.py:18` 和 `scripts/significance.py:14` 都 import 了）。
- 后果：① 推翻 `HANDOFF.md` §4.3 的"CLI、report.html、ablation.svg 都读同一份实现——三处不可能各说一套"；
  ② report.html 印的是 **2/192**，正是第一轮审阅者已指出"偏乐观"、作者已在别处改掉的值；
  ③ report.html 是简历上放的链接，招聘方第一个点开的就是它。
- 修法：删掉 `report.py` 的本地实现，改 `from . import stats`。
