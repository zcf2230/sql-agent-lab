## 1. ReAct 循环 `sqlagent/agent.py`

一次 turn = 一次模型调用；如果它要求调工具，就执行、把结果以 `role=tool`
追加回消息列表，再进下一轮。终止条件只有两个：模型返回时不带 tool_calls，或者步数
预算用尽。

最关键的一行是 `final_sql = last_ok_sql or 散文回退`：**优先取最后一条真正执行成功的
SQL**；只有在该题一次都没执行成功时，才回退去解析 ```sql 代码块，并同时把
`stop_reason` 标成 `no_sql_executed`、在汇总里单独计数。

措辞纪律（这条被外部审阅者抓过一次，别再犯）：**不要说成"永不从散文取"**。那是个全称
否定，一个反例就拆穿，而反例就在数据里——Qwen 3-shot 有 45 道题零工具调用，它们正是走
回退路径被计分的。设计本身可辩护（协议漂移正是本项目自己发现并披露的混淆变量），
**卖点在于"回退会被标记和单独披露"，不在于"绝不回退"**。面试时这样说不但没风险，
反而展示了你能区分"策略"和"绝对化的策略宣称"。

步数预算（`max_steps=8`）不是装饰：没有它，一个反复触发同一个错误的模型会把整轮评测
拖死并且成本无上限。

## 2. 只读执行层 `sqlagent/db.py` + 安全护栏 `sqlagent/safety.py`

两道独立防线。

护栏用 sqlglot 解析出 AST，要求：恰好一条语句、根节点是 `select/union/intersect/except/values`
之一、表名都在已披露的 schema 里、不碰 `sqlite_*`。

这里值得讲的点是**为什么用白名单而不是黑名单**。黑名单要列全
DROP/DELETE/UPDATE/INSERT/ATTACH/PRAGMA/COPY/…，漏一个就完蛋；白名单只要根类型不在
允许集合里就拒绝，新增的怪异语句默认被挡。攻击样本全部被拦（条数以
`tests/test_safety.py` 的 `MUST_BLOCK` 为准，不要背数字——它会随修复增长）。

第二道是连接本身用 `file:...?mode=ro`。就算绕过 AST，SQLite 层也写不进去。
超时用 `set_progress_handler` 实现——`sqlite3` 没有查询超时参数，只能靠进度回调里
返回非零主动打断。行数上限同理：一个笛卡尔积会同时拖垮评测和你下一次调用的上下文窗口。

## 3. 判分器 `sqlagent/eval/scoring.py`（面试主战场）

**它的政策是：宽松于"表述"，严格于"事实"。**

- 列顺序：按列名做置换对齐，(name,total) 和 (total,name) 算同一个答案
- 行顺序：**只在题面要求时检查**
- 浮点：1e-4 绝对容差
- 字符串：折叠大小写和首尾空格
- `2025-03-04` 与 `2025-03-04 00:00:00` 视为相等（库里两种格式真实共存）
- 多出的重复行：**必须判错**——JOIN 扇出是 Text-to-SQL 最高频的真实错误，把它放过
  等于废掉整个指标

两个我主动排除的"虚高来源"：

1. **空集对空集不算命中**（`trivial`，8 题被排除）。模型返回一个语法正确但条件写错
   的查询，常常两边都是 0 行——这什么都没证明。
2. **并列的 top-k 不检查顺序**。`ORDER BY count DESC LIMIT 10`，第 10 名和第 11 名
   count 相同时不存在唯一正确序列，严格比顺序等于抛硬币。

## 4. 为什么"是否要求顺序"是数据集属性，不是 SQL 特征

这是我在这个项目里最想讲的一个判断。

最初的实现是 `ordered = has_order_by(gold_sql)`，看起来完全合理。错在哪：我写 gold 时
习惯在分组统计后面加 `ORDER BY n DESC` 纯粹为了人看着方便，题面根本没要求顺序。于是
一个答对了行、只是顺序不同的答案被判错——**基准在惩罚一个它自己没提出的要求**。

反过来也错：gold 有 `ORDER BY` 不代表题目要求顺序。

所以正确的做法是把 `require_order` 做成任务字段，从**题面**推导（"highest first"、
"top 5"、"ordered by"），再叠加两个约束：gold 必须有可解析的外层 ORDER BY；并且
builder 会把 ORDER BY 表达式解析到输出列、去掉 LIMIT 重跑一次，如果切分点两侧排序键
相同就把顺序检查关掉。208 题里 25 题因此关闭了顺序检查。

## 5. 校准扫描：谁来审计审计者 `scripts/calibrate.py`

benchmark 的数字全部来自判分器，所以先测判分器。方法是往 gold 里注入 6 类已知缺陷，
看判分器的裁决和"应然"是否一致。

设计上有三个坑，都踩过了：

**坑一：`applied` 不等于"结果变了"。** 给一条只返回 1 行的查询加 `LIMIT 3`，文本变了、
`applied=True`，但答案没变——判分器接受它是**正确行为**，如果按"应当拒绝"去统计，
就得到 35% 的假漏判率。修法是把"是否实质改变结果"算出来（`result_changed`），期望值
由它推导，而不是我手填一张 `EXPECTED` 表。

**坑二：审计者比被审计者更严。** 第一版"实质变化"用浮点精确比较，于是
`ROUND(x,1)` 产生的 1e-5 尾差被报成判分器漏判——1 个 false-accept。但判分器容差就是
1e-4，接受它才对。修法：比较键把浮点量化到判分器自己的容差刻度。

**坑三：`bad_column` 注入后测不到东西。** agent 修复成功后提交的正是 gold，结果零差异，
于是 `result_changed=False` → 期望接受 → 一致。它的真实信号在
`self_repair_recovery_rate`，不在这张表里。校准表要能告诉你**哪些条件是控制组**。

最终 778 次观测、0 false-accept、0 false-reject。

被问"你怎么保证你的评测是对的"时，答案不是"我看了几条觉得没问题"，是这张表。

## 6. Mock Provider 为什么存在

`MockProvider` 是一个**知道标准答案、按脚本行动、可以被注入缺陷**的假模型。它让
整条链路（prompt → 工具 → 执行 → 判分 → trace → 缓存 → 汇总）在零 API 花费、零网络
的情况下可测试。CI 里跑的、`python -m pytest` 验证的都是它。

写它时踩的一个真 bug：判断"上一步工具是否成功"时用了
`'"ok": true' in json.dumps(content)`。`content` 本身已经是 JSON 字符串，`dumps` 会把
里面引号转义成 `\"ok\": true`，子串**永远匹配不上** → 模型以为每次都失败 → 无限重试
到步数耗尽。修法是解析而不是搜子串。

另一个：只看 `role == "tool"` 就以为 SQL 跑过了，于是 schema 一返回就直接收尾。
必须按工具名分支。**"任何工具返回"和"我的查询已执行成功"是两件事。**

## 7. Runner 的缓存和回归门禁

`config_hash` 由 provider/model/temperature/max_steps/self_repair/fewshot_k/
prompt_version/seed 组成，缓存键是 `(config_hash, task_id)`。所以改 prompt 时**必须**
同步 bump `PROMPT_VERSION`，否则你会拿旧分数评价新 prompt。

回归门禁解决的是 prompting 的本质问题：**它是反射式编程**。你为了修好第 41 题改了一
句提示词，很可能悄悄弄坏第 12 和 19 题，而 pass@1 从 0.71 涨到 0.72，看起来是进步。
`--check-baseline --strict-gate` 会把正确→错误的题目列出来并返回退出码 1，让这种
"进步"过不了关。

## 8. 最有价值的一个 bug：few-shot 让准确率从 89.6% 掉到 3.7%

这是我在这个项目里最想讲的一段，因为**它一开始看起来像一个实验结论**。

我把 `--fewshot-k 3` 接好之后跑消融，pass@1 从 0.896 崩到 **0.0365**，
`column_count_mismatch` 从 7 涨到 95。任何一个粗心的做法都会把这写成
"few-shot 在我们的场景里没有增益反而有害"——一个听起来很合理、可以被直接写进简历的
"发现"。

打开 trace 看第一条就知道不是。`filter_projection-001` 问"Beijing 有多少用户"，
模型答的是 `SELECT level, COUNT(*) AS n FROM courses GROUP BY grp ORDER BY n DESC`。
**那字面上是另一道题的 gold SQL。**

原因在 `build_messages` 的拼装顺序：

```python
messages = [system, user(target)]      # 目标题放在第二个位置
for turn in fewshot: messages.append(turn)   # 示例追加在最后  ← 错
```

于是模型看到的**最后一条消息是某个示例的 assistant 答案**。它做的事非常合理——
从那里继续，把最后一个示例答完，根本没理你的目标题。

正确顺序是示例在前、目标题在最后。修完 3-shot 回到正常区间。

**这件事有三层可以讲：**

1. **表层**：few-shot 拼接顺序错了。听起来很蠢，但 `[system, user, ...demos]` 这种
   写法非常自然，而且它不报错、不崩溃，只是安静地给出一个可解释的坏数字。
2. **中层**：为什么我能发现？因为我保留每条结果的 `final_sql` 并去比对它是否
   **恰好等于另一道题的 gold**。只看汇总数字（3.7%）我大概会去调 k、调示例条数，
   然后写下一个假结论。**看失败样本的具体内容，而不是只看比率**，是唯一能区分
   "bug"和"发现"的手段。
3. **深层**：为什么这个 bug 存在这么久？因为在这之前 `--fewshot-k` 是个**假开关**——
   它进了 `config_hash`、进了汇总输出，但没有任何代码把示例传给 `agent.run()`。
   一个从不生效的参数不会暴露自己的拼装 bug。所以我为它写了
   `tests/test_fewshot.py`：断言 `messages[-1]` 必须是目标题、断言 k 会真的改变
   prompt 长度、断言示例里不含目标题自己（**示例泄漏**是 Text-to-SQL 最廉价的作弊
   方式）。

如果面试官问"你遇到最难 debug 的问题"，就是它——难点不在修，而在**意识到一个看起来
像结论的数字其实是 bug**。

## 2.5 外部审阅者当场拆掉的一个洞（必读）

我原先写"白名单只允许读根节点"，并把这当成卖点。审阅者构造出：

```sql
WITH d AS (DELETE FROM users) SELECT * FROM d
```

**根节点是 SELECT，所以它过了白名单。** 我测的是 `DELETE ... RETURNING` 那个变体——
恰好是更难绕的那一个。UPDATE / INSERT 的无 RETURNING 形式同样放行（我实测确认过）。

没造成危害，靠的是另外两层：SQLite 不支持 DML-in-CTE（语法层）+ 连接是 `mode=ro`。
**也就是说：一个方言巧合在替我的"检查"层兜底，而我在文档里把那层说成了防线。**
这才是这个洞真正的代价——不是被绕过，是我的"分层防御"其实没有分层。

修法是把检查从"看根节点"改成"任意深度出现 DML/DDL 节点即拒绝"，并加一条测试断言
**节点名单没有因为 sqlglot 改名而静默变薄**（那份名单是用 `getattr` 取的，改名会让它
悄悄降级成零，而所有测试照样绿）。

**如果面试官问"你这套护栏真挡得住吗"**，就照这个讲。承认"我曾把一个方言巧合当成自己的
防线，是外部审阅者发现的"，比背"我们有三层防御"强得多——后者一戳就破，前者说明你知道
每层各自在挡什么。

    顺带：19 个族里 15 个净变化为 0，"+4.2pp"实质是"两个族里 12 道题变了"。）

26. **（第三轮之后自问，但面试官一定会问）** 你说 pass@1 是 89.1%。
    那道题**换一种问法**还是这个数吗？
    （答：**两个方向都量过了。**
     低估侧——baseline 判错的 21 题是**全部**非 trivial 失败题，是普查不是抽样：
     **4 道（19%）换个说法就做对**，直接换算成 **4/192 = 2.08pp**，不用乘系数。
     高估侧必须按族占比抽样才有效：判对的题抽 22 道，
     **1 道（4.5%，Wilson 95% [0.8%, 21.8%]）换个说法就判错**，折回头条是
     4.0pp（"换一种说法即判丢"口径）或 1.0pp（"四种说法各跑一遍取平均"口径）。
     成功侧**第一次我做砸了**：抽"每族第一题"看着像分层抽样，实际是专挑每个族最简单的
     那道，19 题四种问法全对、零区分力——那次的产物至今留在仓库里。
     重看结论不花钱：`--pick failures` 与 `--pick correct-representative` 各加
     `--analyse-only`，两个数都由脚本自己换算。）
    （考的是三件事：① 你敢不敢把做砸的那次留在仓库里并说出来；② 你知不知道 19%
     选在"有失败的地方"、不能乘到全卷，而 4.5% 那组才可以；③ 你能不能说清 4.0pp 和
     1.0pp 是**两个不同问题的答案**（差在"一道题四种问法里错几种"）——报数时不声明
     口径，就是在替读者做选择。）
