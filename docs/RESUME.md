## 版本 A · 算法 / 大模型算法实习

> **Text-to-SQL 智能体的评测方法学与消融研究**（独立项目 · Python · 85 个单元测试）
>
> - 自建**可自动判分基准**：20 表业务库（800 用户 / 2.2 万行为记录）注入 7 类数据陷阱；
>   192 道题由参数化模板生成，**每题 gold SQL 均实际执行校验**，题面所有过滤值由数据库
>   `SELECT DISTINCT` 反查（早期手写值池导致 9 道题询问库中不存在的城市，使最简题型
>   通过率虚降至 55%）
> - 以**执行准确率（Execution Accuracy）**为指标并显式化判分政策：列序按列名对齐、
>   行序仅在题面要求时检查、浮点容差 1e-4；主动排除两类虚高命中——空集对空集、
>   排序键并列的 top-k。**共剔除 14 道不可判定题目并逐条记录原因**
> - **审计判分器本身**：注入 6 类已知缺陷，由"缺陷是否实质改变结果集"自动推导应然裁决，
>   **750 次观测零误判 / 零漏判**；期间修复校准器与判分器容差刻度不一致导致的假漏判
> - 用**配对检验**约束结论：3-shot 使 pass@1 从 89.1%（Wilson 95% CI 83.9–92.7）升至
>   93.2%（88.8–96.0），**McNemar 精确双侧 p=0.057，明确标注为未达显著**；自修复开关
>   逐题结果零变化（p=1.0）。噪声底取四份同配置基线的最大两两差异 2.1pp 作为可报告
>   增益阈值。以上统计量由 `scripts/significance.py` 产出，文件名与配对写死在代码里
> - 识别一处**混淆变量**：Qwen-flash 的 3-shot 表面提升 4.7pp，实为示例格式（不含工具
>   调用）改变了执行协议——仅 24% 的题目真正运行过查询，45 题零工具调用；
>   因此跨模型能力对比**结论为未答**

**追问预案 —— "为什么不用 Spider / BIRD？"**

> 因为我要能审计判分器。公开基准的判分脚本对空集、列序、并列 top-k 的处理是我无法
> 验证的黑盒；我要的是"每项宽松政策我知道理由和代价"。代价是**牺牲与公开榜单的
> 可比性**——我不声称和 Spider 分数可比。

**加分句 —— "最大的不确定性是什么？"**

> p=0.057。样本量再大一倍才敢说是提升。我现在能说的是方向为正、且没有任何一题
> 因判分政策被误判。

## 版本 B · Agent 应用 / 智能体开发实习

> **Text-to-SQL 智能体系统与可靠性工程**（独立项目 · Python · DeepSeek / Qwen 双模型 ·
> 4,600 行 / 85 个单元测试）
>
> - 实现 4 工具 **ReAct 循环**（`list_tables` / `get_schema` / `sample_values` / `run_sql`），
>   带步数预算、终止条件与报错自修复；**`final_sql` 优先取"最后一条真正执行成功的查询"**，
>   完全没执行过查询的题目单独标记 `stop_reason=no_sql_executed` 并单独披露计数——
>   避免把模型幻觉出的、从未运行的 SQL 混进准确率而无人察觉
> - **上下文工程**：每题平均 4.7 次调用、约 5.7k token；schema 探查与值采样工具用于处理
>   大小写/空格混杂的枚举值（`'BEIJING'` 与 `' Beijing '` 在库中真实共存）；实测单题成本
>   **¥0.006**，同配置重跑走缓存零成本
> - **安全护栏按不可信输入设计**：SQL 经 sqlglot 解析后走 **AST 白名单**（只读根语句、
>   禁止堆叠语句、表名需在披露的 schema 内、屏蔽 `sqlite_*` 目录表），底层再叠 `mode=ro`
>   只读连接与查询超时 / 行数上限；结果集命中指令模式时打 `_security_note` 标记而非静默丢弃
> - 实现 **26 条对抗性安全探测**（样本小、问法未校准，故不给比率）：捕获 6 次越权尝试全部
>   被护栏拦下、零写操作真实执行、零"谎称已删除"；捕获智能体在 `sqlite_master` 被拦后改用官方别名 **`sqlite_schema`**
>   重试，**证明白名单默认拒绝优于危险词黑名单**
> - **可观测性与回归防线**：逐调用 JSONL trace（prompt / 工具入参出参 / token / 耗时 /
>   错误类型）可全量回放；结果缓存键包含数据集与判分器源码摘要，杜绝"改完判分器吃旧分数"；
>   回归门禁列出正确→失败的具体题目并返回非零码
> - 修掉 5 个**会静默产出假结论**的缺陷：few-shot 配置项未进入 prompt、示例拼接在目标题之后
>   （模型照格式答完上一个示例，pass@1 崩至 3.65%）、题面引用不存在的数据、幻觉列名穿透
>   工具层导致整题崩溃、交付测试误删真实凭据且一路绿灯

**追问预案 —— "用了什么 agent 框架？"**

> 故意没用 LangChain / LangGraph，自己写的循环。理由是我需要一个能解释到第三层的系统。
> 但我读过 LangGraph 的状态机实现，我这一版的差异是状态转移就写在 `agent.py` 里、
> 可观测性靠自研 JSONL trace，代价是没有生态。

## 两版共用的三条底线

1. **项目定位行按岗位切换**，同一份代码两套卖点，不冲突。
2. **三句话任何岗位都不要写**：
   - "100% 拦截危险语句" → 正常题里护栏触发 0 次，只有 26 条探测给出过证据
   - "自修复提升准确率" → 实测逐题零变化
   - "跨模型验证了能力" → 被工具服从度混淆，未答

   主动说"这个我没测出来"比藏住它加分。
3. **被问"哪部分是你做的"**（一定会问，代码由 AI 助手实现）：

   > 代码大部分由 AI 编程助手实现，但每个数字都是真跑出来的。我能说出判分器在哪些维度
   > 宽松以及为什么、能说出 3-shot 那个 3.65% 是怎么从拼装顺序来的、能说出护栏在正常题里
   > 一次都没触发所以那个数字不算证据。第九个坑是我自己的一个测试删掉了真凭据文件还一路
   > 绿灯——这种事藏不住，我也没打算藏。

   配合 `git log --oneline` 一起看——历史里相当比例的提交，标题就是"修正我自己产出的假结论"。
   **具体比例和提交数故意不写进来**：任何写进文档的计数，在写下的那一刻就开始过期，
   而这个项目一整轮都在处理这种漂移。
