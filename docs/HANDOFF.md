## 0. 30 秒版

做了一个会写 SQL 的 AI agent，**但主要工作量花在"怎么知道它的分数是真的"上**：
自建 192 题基准 → 自建判分器 → **反过来审计判分器**（注入 6 类已知缺陷，750 次观测）
→ 用配对统计检验约束结论 → 用对抗探测给"安全性"补上真实证据。

结果是三层可信度递减的数字：

```
判分器：750 次注入观测，0 误判 0 漏判；搬到别人写的题上（BIRD dev 120 道人写 gold）120/120 自洽   ← 最硬
        同一批数据上，公开基准自己的 EX 看不见 13 条重复行里的 11 条；
        而我在列序与舍入上比它宽松        ← 两个方向都报；测的是判分器，不是 agent 得分
DeepSeek pass@1 89.1% → 93.2% (3-shot)      ← 真数字，但 McNemar p=0.057，未达显著
同题换问法：判错的 19% 换问法即对、判对的 4.5% 换问法即错
        换问法：判错的 19% 换问法即对（低估 1.30–2.08pp）
        判对的 4.5% 换问法即错（高估 1.0–4.0pp）  ← 一次问法=一次抽样，不是测量
安全性：26 条探测里模型实际尝试 6 次，6 次全是读形状   ← 不给比率；
        写路径尝试数 = 0，也就是那一侧根本没测到
```

审阅时最该关注的是**第二行的 p 值、第三行的抽样规则、第四行的样本量**，
作者没有把它们藏起来（§17 记录了第三行那次先做砸的尝试）。

### 4.3 核对统计量（已入库，`scripts/significance.py` 现算）

统计逻辑在 `sqlagent/stats.py`：它是唯一实现，CLI、`report.html` 与
`docs/figures/ablation.svg` 都读它——三处不可能各说一套。跑 §4.2 里那条
`python scripts/significance.py` 就能对上一整张表。

**哪份运行文件参与配对**也写死在 `stats.py` 里，并带了理由注释：`abl-baseline`
故意**不**与 `abl2-3shot` 配对（它早于 few-shot 接线，配它就是跨代码版本比分数）。
一位审阅者这样配，得到的是 p=0.092 而不是文档里的 0.057——这个清单就是这么来的。
`tests/test_stats.py` 把下面三个 p 值钉住，锚点正是那位审阅者独立手算的结果。

| 对比 | 修好 / 弄坏（配对不一致） | Δ | McNemar 双侧精确 p | Wilson 95% CI |
|---|---|---:|---:|---|
| DeepSeek 3-shot vs baseline | 11 / 3 | +4.2pp | **0.057** | 83.9–92.7 → 88.8–96.0 |
| DeepSeek 关自修复 vs baseline | 0 / 0 | 0.0pp | 1.000 | 同左 |
| Qwen 3-shot vs baseline | 23 / 14 | +4.7pp | 0.188 | 63.5–76.3 → 68.4–80.6 |

**结论：没有任何一项能靠「显著/不显著」这个二说来陈述。** 89.1%→93.2% 是真实观测；题级 p=0.0574，但按骨架聚合后 p 在 0.039–0.227 之间跨过 0.05，所以这里报方向、效应量、区间与这个不稳定性，不报显著与否。

## 6. 已知未证明 —— 请勿把这些当结论引用

1. **自修复无增益**（逐题结果零变化）。原因不是功能坏，是模型首次即成功率高
   （`avg_sql_attempts` 1.01）→ 没有错误可修。机制靠注入单独验证：开 96.2% / 关 0%。
2. **跨模型能力对比无效**。被"工具调用服从度"混淆：Qwen 3-shot 仅 24% 的题真跑过查询、
   45 题零工具调用。**"哪家模型更会写 SQL"目前无答案。**
3. **安全护栏的行为证据只有 26 条探测，而且写路径一次都没被测过**。192 道正常题里触发
   **0 次**；26 条里模型实际只尝试 6 次，且**全部是读形状**（查目录表、`INTO OUTFILE`、
   运维语句），`direct_write` 那 6 条它一次都没试。所以"0 次写操作执行"是平凡成立——
   护栏从未被问过写语句。所以那一格既不给比率，也不写成"拦住了"这种完成式——
   旧版这里原文照抄过被禁的说法来禁止它，第四轮 F8 指出：那样这条禁令本身就变成了
   被禁字符串的载体，一致性测试永远接不住它。
4. 只测了 temperature 0、单轮、两套 prompt、一个 seed。
5. 题目全部来自参数化模板 → 措辞比真人写的整齐。**改写鲁棒性两侧都测了（§17）**：
   baseline 判错的 21 题（= 全部非 trivial 失败，是普查）里 **4 道（19%）换一种问法就
   做对**，即 pass@1 **低估**：按题 4/192 = 2.08pp、按四种问法取平均 1.30pp
   （第四轮 F2 指出这里曾只报大的那个，而高估侧一直两个都报）；反向按族占比抽 22 道判对题，
   **1 道（4.5%，Wilson [0.8%, 21.8%]）换一种问法就错**，换算到头条是 1.0pp（取平均口径）
   到 4.0pp（"换一种说法即判丢"口径）。两边都不是"模型不行"，而是"一次问法只采到一个样本"。
   此处旧版先后写过"只缓解一部分"和"成功侧无从判断"：前者描述一个当时还没做过的实验，
   后者描述做砸的第一次。成功侧 n=22，只用于判断量级，不构成可发布的修正系数。
6. `drop_distinct` 缺陷只有 6 题能承载，而它是最真实的错误类型——**且这 6 题全来自同一个族**。
7. 判分器按列名做置换对齐；两个匿名表达式退化为按位置比较，此时列交换看不见。
8. 成本是**估算**：DeepSeek 单价从控制台实扣反算，Qwen 是单次账单推出的**混合单价**
   （97.3% 输入，分不出输入/输出价）；未录入的模型显示"单价未录入"而不是 0。
9. **192 题去重后只有 100 个 gold SQL 骨架**，McNemar 的题级独立性假设不成立。
   按骨架聚合后 p 在 0.039–0.227 之间跨过 0.05，所以"显著/不显著"这个二分**不是结论**，
   方向、效应量与区间才是。复现：`python -c "from sqlagent import stats;
   print(stats.cluster_sensitivity('abl2-baseline','abl2-3shot'))"`。
10. **"谎称已完成 = 0"同时是检测器召回的测量值**。匹配器已覆盖被动/完成时/名词前置/中文
    （12 个表述命中 11，7 个拒绝句零误报），但它仍是正则；原始命中数 `claims_matched`
    与扣除拒绝后的 `claimed_done` 并列输出，就是为了让人能分辨这两件事。
11. **难度标签是族级常量**，一个族一个值、族内零变异，实为 SQL 结构复杂度；
    且分桶极不均（`hard` 的 63 题里 35 题来自 `category_slice` 一族）。
    所以"easy/medium/hard 三档通过率"不能当作难度分析引用。
12. **trace 文件本身带着洞**：加锁之前的并发追加撕坏了记录，本机 `runs/` 数出 64 行不可解析；报告第 9 节披露的是其中影响它自己显示的那 2 题（`runs/` 不入库，所以 clone 出去只核得上这 2 题，64 那半句话请以本机重跑为准）。**逐题结果与分数不受影响**（那些在 `results/`，由 runner 单写），但「这一题的过程我看不全」是一个已存在的事实，不是假设。复现：`python -m sqlagent.report` 的最后一行。
13. **BIRD 实验只检验了判分器，没有检验 agent**：120 题、SQLite 方言、`require_order` 一律 False（**顺序敏感性未测**），也没有跑过任何模型做 BIRD 的题，所以这里没有、也不该有"BIRD 上多少分"。判分器与公开口径的差是双向的：我在重复行上更严（11 条官方看不见），在列置换与舍入上更宽松（34 + 28 条）。见 §19。

```bash

#   ✅ 已做（2026-09-22，push 之前）：38 个提交的作者/提交者邮箱全部重写为
#   GitHub 的 noreply 地址。验证方式（三条都过了）：
#     git log --all --format='%ae %ce' | grep -c gmail   -> 0

## 17. 同题重述稳定性：四组样本，误差的两个方向

`python scripts/restability.py --pick <方式>`。四组产物各自独立命名：

| `--pick` | 选题规则 | 题数 | 产物 | 可外推？ |
|---|---|---|---|---|
| `families` | 每族第一题 | 19 | `results/restability-deepseek-chat-families.jsonl` | 否（无区分力，见"结果〇"） |
| `failures` | baseline 判错的全部题 | 21 | `...-failures.jsonl` | **是**，但它是普查不是抽样 |
| `correct-representative` | baseline 判对的题按族占比抽 | 22 | `...-correct-representative.jsonl` | **是**（唯一一组） |
| `correct-boundary` | 判对题里专挑同骨架有对有错 + 边界族 | 20 | `...-correct-boundary.jsonl` | 否（刻意过采样不稳定） |

**重看结论不花钱**：加 `--analyse-only` 就只读已提交的产物并重印，例如
`python scripts/restability.py --pick correct-representative --analyse-only`。
本节每个数字（含外推与 Wilson 区间）都由这条命令产出。算术在 `sqlagent/stats.py`
的 `restability_report()` 里，脚本与 `report.html` 第 3 节共用它——有一条测试禁止
`report.py` 自己另算，正是当年噪声底两处各说一套之后加的。`tests/test_artifacts.py`
断言四组产物与各自的 `data/tasks_restability-*.jsonl` 逐 id 对应——因为这两类文件
曾经同名过（§9-22）。

### 为什么做这个

三轮审阅都指向同一句话：**现在没有任何数字能回答"模型是在解题还是在认模板"**。
基准每题只被问一种问法，所以 pass@1 无法区分"理解了问题"与"认出了句子"。
这是本项目所有分数的共同前提，而它此前从未被检验。

### 方法

不新造问法——用**生成器自己的**模板。每道题：

1. 从存档题面反推裸题面（剥掉模板前缀）。反推用**往返校验**把关：
   把还原出的裸题面重新套回那个模板，必须与存档题面**逐字节相同**，否则该题跳过并报告。
   四组选题（19 / 21 / 22 / 20 题）全部通过，无一跳过。
2. 用全部 **4 种**去重后的模板各生成一问。（顺带实测确认第三轮的 D10：
   `PARAPHRASE` 声明 5 项，`"{q}"` 出现两次，**实际只有 4 种**。）
3. 同一 gold SQL、同一 `require_order`、同一 `score_execution` 判分。只问题面。

### 结果〇：成功侧第一次尝试（19 题 × 4 问法 = 76 次，$0.066）——**做砸了，产物仍保留**

选题规则是"每个模板族取第一题"，结果 19 题**四种问法全对**：一致率 100%，翻脸 0 道。
**这不是"模型很稳定"，这是零区分力**——没有可动摇的东西，当然测不到动摇。判分器审计里
我批评过同一件事（某格缺陷根本到不了答案，那个 100% 就不是证据），这次犯在自己身上。
它留在仓库里，因为"每族取第一题"看着像分层抽样，实际是刻意挑每个族最简单的那一道。

### 结果一：失败侧（21 题 × 4 问法 = 84 次，$0.079）

| 事实 | 数 |
|---|---|
| 四种问法全错（失败与措辞无关，是真不会） | **17/21** |
| 换一种问法就做对（失败是措辞造成的） | **4/21 = 19%** |
| 其中"只有基准那种问法失败、其余三种都对" | 3 道：`group_by-007`、`metric_by_group-006`、`category_slice-031` |

**读法**：pass@1 **低估**了模型。那 3 道尤其难看——基准挑的那种问法恰好是四种里
唯一失败的一种。而且这 21 道是 baseline 全部非 trivial 失败题的**普查、不是抽样**，
所以换算不用乘系数。**但口径仍然有两个，而且必须与高估侧用同一套名字**（第四轮 F2：
此前这一侧只报了大的那个，而高估侧一直两个都报）：读法 A「换一种说法即得分」
`4/192` = **2.08pp**；读法 B「四种问法取平均」`2.50/192` = **1.30pp**——那 4 道里
`category_slice-014` 四种问法只对 1 种，按平均只值 0.25 道。两行都由

### 结果二：成功侧·可外推那一组（22 题 × 4 问法 = 88 次，$0.077）

选题规则：baseline 判对的题，**按各族在其中的占比**抽 22 道（`select()` 里唯一

**换算回头条 pass@1（89.06%）有两种读法，差 3pp**，所以必须说清问的是哪一个：

| 读法 | 问的是什么 | 结果 |
|---|---|---|
| A「换一种说法即判丢」 | 多少已得的分是**靠那一种措辞拿下的**（换一种就有一败） | 89.1% × 4.5% = **4.0pp**（区间 0.7–19.4pp） |
| B「四种问法都算一遍取平均」 | 若基准对每题平均而言给多少分 | 89.1% × 1.1pp = **1.0pp** |

两者差在"一道题四种问法里错几种"：`group_by-001` 错 1/4，所以 B 只扣 1/4 份。
两行都由 `--pick correct-representative --analyse-only` 打印。

### 结果三：成功侧·刻意挑边界（20 题 × 4 问法 = 80 次，$0.079）

选题规则：6 道与失败题**共用同一 gold 骨架**（同一种查询、换参数值）+ 其余按族轮转
每族 ≤2 道，从"含失败题的 8 个族"补足到 20。**刻意过采样不稳定，不可外推**——
它回答的是"最坏边界上有多脆"，不是"全卷有多少脆"。

结果：**2/20 = 10% 换一种问法就错**，两道都是 `group_by`（`group_by-001`、`group_by-002`）。

### 合起来读

1. **误差两个方向都测到了，而且不在同一批题上**：低估 1.30–2.08pp（普查，确切）、
   高估 1.0–4.0pp（n=22，区间宽）。**它们不抵消**——把两边相减报一个"净偏差"
   就是把两个不同抽样、不同分母的数拼成一个不存在的量。
2. 单种问法给出的 pass@1，**是一次抽样而不是一个测量**。这次实测的抽样噪声
   （±1–4pp）与 §6-9 骨架聚合造成的 p 值漂移（0.039–0.227）是同一件事的两个侧面：
   基准的不确定性主要来自"怎么问"和"怎么归并"，不是来自模型。
3. 一个**线索**（不是结论）：三个成功侧样本里翻脸的题全部落在 `group_by` 族
   （`group_by-001` 同时出现在两组样本里、`group_by-002` 在边界组、失败侧的
   `group_by-007` 换问法即对）。`group_by` 只有 10 题，**这足以让我下次多问它几题，
   不足以说"group_by 对措辞敏感"**。

### 这次花掉的钱与留下的教训

四组共 328 次调用、实花 **$0.301 ≈ ¥2.2**（每组成本由各自产物的 `cost_usd` 求和，
上表逐组标注）。其中 **$0.066（结果〇）买到的是一条"实验设计无效"的结论**。
按 §16.6 那条判据衡量：它没有改变任何已发表判定，只是让我知道下一版该怎么选样本——
这笔钱不亏，但**必须连同失败一起报**，只报 19% 那一半就是这份材料最反对的做法。

另外两次不是实验错误、是工程错误，已进 §9：结果文件名不含 `--pick`，第二次运行
覆盖了已提交的第一次产物（§9-22）；`--model` 只改标签不改端点，一批 80 次调用
全打到 DashScope 上 404（§9-23）——**runner 的"测量失败不得读成模型分数"这道闸
把它接住了**，报的是 `harness_exceptions=80 / pass@1 拒绝输出`，不是一个假的 0%。

### 仍然成立的限制

n=22 是唯一可外推的一组，4.5% 的区间宽到跨一个数量级，**不构成可发布的修正系数**。
四种问法之间的语义距离不等（`Using the platform tables, ...` 与
`Please answer with SQL, ...` 比裸题面更接近彼此），所以"4 种问法"不是 4 次独立抽样；
上面所有除以 4 的口径（读法 B）都因此偏乐观。
边界组的族分布仍偏向 `category_slice`（20 题里 8 题，全卷占 18%），所以 10% 这个
上界也带着这个偏向。

## 19. 把判分器搬到公开基准上：BIRD dev 实测

前三轮审阅共同的结构性弱点，是我自己 §6 写着的那条：**题是我造的、gold 是我写的、
schema 没人见过**。自审能证明判分器*自洽*，证明不了它测的是这个领域所说的执行准确率。
所以这次把同一个判分器搬到 **BIRD dev**（11 个真实 SQLite 库、1534 道人写题）上跑，
并与**公开基准自己的比较规则**逐条对齐。全程 $0、不调模型：注入的变体由
`sqlagent.llm.corrupt` 本地生成，判分本来就是 (gold, pred, 数据库) 的纯函数。

`python scripts/bird_judge.py --per-tier 40`（数据下载方式在脚本 docstring 里；
它故意不进 CI——346 MB 的第三方下载不该塞进构建）。

### 19.1 样本与做法

- 选题：BIRD 自带 `difficulty` 三档各取 **前 40 个 question_id**（排序后取前 N，无随机、
  无挑选），共 120 题、11 库全解出（1.49 GB 未压缩）。
- 公开口径不是我猜的：`bird-bench/mini_dev` 的 `evaluation/evaluation_ex.py:20` 就是
  `set(predicted_res) == set(ground_truth_res)`。我在 `scripts/bird_judge.py` 里复现同一条
  规则，并用 `tests/test_bird_judge.py` 把两套比较规则的语义各钉住（重复行、列序、行序、
  缺行各一个最小用例）。
- 逐类报告被排除的题，不静默丢弃：注入不进去的（107 道题没有 DISTINCT 可去）、
  `corrupt()` 解析不了的（7 条 gold）都单独计数。

### 19.2 结果

| 检查 | 结果 |
|---|---|
| gold 判 gold（自我一致性，真实人写 SQL） | **120/120** |
| 6 类注入 × 可承载的题 | **460 条观测，与我自己的政策一致 460/460** |
| 与公开口径的分歧 | 见下，双向都有，逐类列出 |

| 注入类 | 可比观测 | 与公开口径一致 | 分歧方向 |
|---|---|---|---|
| `reflow` 重写同义 | 62 | 100% | — |
| `reorder_cols` 列置换 | 34 | **0%** | 公开口径按位置比较，判错；我按列名对齐，判对 |
| `float_round` 舍入 | 113 | 75.2% | 28 条公开口径判错（数字不同），我按容差判对 |
| `drop_distinct` 重复行 fan-out | 13 | **15.4%** | **11 条官方 EX 看不见**，我判错 |
| `wrong_limit` 行数错 | 118 | 98.3% | 2 条官方看不见 |
| `bad_column` 列名不存在 | 120 | 100% | 两边都判错 |

**这次真正值钱的两句**：

1. **公开基准的执行准确率看不见重复行 fan-out**：13 个能注入的 DISTINCT 移除里
   **11 个被官方口径判成正确**（`set()` 折叠了重复行）。而重复行正是我在 §3 校准表里
   标的"最高频的真实错误类型"。也就是说：在公开榜上刷高分的系统，可能根本没被要求
   区分"多出一倍重复行"和"答对"。
2. **我不拿这条冒充"我比官方严"**：同一批数据上，我在列置换（34 条）与舍入（28 条）上
   比官方**宽松**。所以正确的说法是两个方向各自的差与原因，而不是一个总判断。

### 19.3 它顺手抓出来的两个自家 bug（这才是搬家最大的收获）

搬到真实数据的第一轮，`vs policy` 不是 100%，而是 93%/91%/83%——三个类的"应然值"与
判分结论互相矛盾。查下去是两个真 bug，都不是合成数据能暴露的：

1. **`result_differs()` 比较列名，而判分器不比列名**。于是"反引号写成双引号"这种纯
   拼写差异被记成"结果变了"，而 192 题自制数据里投影永远是命名列，看不见。
   后果直接打到已发布的校准表：`reorder_cols` 那 192 行里有 **58 行**一直记着
   "注入改变了结果"，同时判分器判"接受"——**我用来自那 750 条解释"缺陷有没有碰到答案"
   的那一列，自己就是错的，而 750 的主指标一直是 100%**（政策类缺陷不计为 false-accept，
   所以矛盾藏在解释性列里，不在红绿灯里）。
2. **列标签的拼写噪声会击穿按名对齐**：表达式列的标签就是它自己的文本
   （`'( SELECT … )'` vs `'(SELECT …)'`；``T1.`x` `` vs `T1."x"`）。对齐失败会
   **静默退化成按位置比较**，于是政策上该接受的列置换被判成 `value_mismatch`。
   §6-7 早就写了"两个匿名表达式退化为按位置比较"，这次是同一机制的第 2、3 个真实案例。

两个都在 `sqlagent/eval/scoring.py` 修掉（列标签归一化 + `result_differs` 与判分器共用
同一种"答案相同"的定义），`tests/test_scoring.py` 用 q94 / q77 / q1 / q62 四道真实题
钉成回归用例。

### 19.4 修完之后，公布过的数字动了吗——没有，而且是算过的

判分器改动会影响已发表结论吗？重跑真实模型要花钱，而且会把"打分变了"和"模型这次答得
不一样"混在一起。判分是纯函数，所以 `scripts/rejudge.py` 只做重判：**15 次运行在范围内
（4 次因题集不同被排除），2440 条已存答案逐条用当前判分器重新执行、重新判——192 题集
11 次 × 192 = 2112 条，重述实验 4 组 80/88/84/76 = 328 条——结论翻转 0 条**。
同时 `scripts/calibrate.py` 重算仍是 `OVERALL 750 750 0 0 100.0%`。
唯一变化是校准表里那一列的*意义*（第 1 条 bug 的修正），已在此说明。
脚本自带范围判定：产物自己的 `n_tasks` 与当前题集不符（208→192 那几次旧运行）就
标注 out of scope 并跳过——把它们的重判差异算作"判分器行为变化"，是我第一次跑这个
脚本时差点写下去的假结论。覆盖数由脚本自己打印（`覆盖：… 条已存答案…`），本节那几个
数字抄自它，不手数。

### 19.5 搬家还顺手做了一件事：把读侧的「静默跳过」数了出来

`figures.trace_svg` 在生成本地第四张图时崩过一次，起因是 `runs/` 里有一行不是合法 JSON。顺着查下去，问题不在 BIRD，在**我自己 trace 文件的写侧竞态**（§9-37）：4 个 worker 线程追加同一个文件，一条几 KB 的记录被拆成两次系统调用、两个线程的半条互相穿插。真正的坏味道是**读侧一路 `except: continue`**，所以洞在页面上长成「那里什么都没有」，而不是「那里少了一条」——这一整节讲的正是「静默丢弃分母」的害处，而我自己在一处更靠近数据的地方犯了同一个错。现在写侧加锁、读侧计数并披露（报告第 9 节的红色说明框）。已发布文件里那 64 行撕痕保留原样：重写 trace 等于重跑模型，而分数不依赖它们。

### 19.6 这次没测的（别当成测了）

  没被检验**；官方口径本身对行序盲目。

  结论，也不该有。要那个数需要一轮真实调用（约 ¥0.3–1，几十题）。
